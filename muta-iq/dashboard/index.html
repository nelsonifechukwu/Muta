Muta model optimisation report · July–August 2026

Model selection for the 8 GB CPU target

Muta is an offline tutor for mathematics and scientific reasoning. The submitted GGUF must run on an 8 GB CPU-only laptop. This report compares model accuracy, generation throughput, peak resident memory, and compatibility with the evaluator's runtime.

01

Scoring function

Score components and disqualification conditions

The evaluator runs one GGUF with llama.cpp on an Ubuntu laptop with four CPU cores, 8 GB of RAM, no discrete GPU, and a 7 GB memory limit. The total combines accuracy, generation throughput, peak RSS, and a thermal penalty. A crash, out-of-memory termination, or illegal instruction disqualifies the run.The engine build sets GGML_AVX512=OFF, and the Docker build checks the disassembly for AVX-512 instructions. Zen 3 and several consumer Intel processors do not support AVX-512.

Performance is capped at 15 tok/s, and efficiency is zero at or above 7 GB RSS.S_perf = min(TPS/15, 1) × 100 and S_eff = max(0, (7 GB − RSS)/7 GB) × 100. All evaluated candidates remained below the memory limit. Accuracy is uncapped and contributes 50% of the total. Additional memory is beneficial only when the associated accuracy or throughput increase exceeds its efficiency cost.

Decision rule

An additional 1 GB of RSS requires either 1.43 tok/s or 5.7 accuracy points to preserve the same total. This threshold is applied only within measurements that use the same hardware, binary, and scoring formula.

02

Evidence categories

Five non-comparable measurement categories

The measurements use different machines, binaries, and performance formulas. Results are grouped into five categories. Rankings are computed only within a category unless the comparison controls those differences explicitly.

Official profiler result

Full profiler execution

The published participant executable measures generation throughput and root-plus-child peak RSS. Q4_0 has the highest total under this executable's scalar kernel configuration.

Profiler-parity estimate

No-AVX reconstruction

This configuration reproduces the no-AVX engine policy. Throughput is measured in timed samples. Profiler RSS is estimated by adding a documented 45 MiB root-process allowance to the measured child tree.The allowance represents the Python interpreter and lm-eval imports in the profiler root process. It is an estimate, not a direct measurement.

Controlled AVX2 proxy

Paired ISA benchmark

The same five GGUF hashes were measured with AVX, AVX2, FMA, and F16C enabled, with native tuning and AVX-512 disabled. Q4_K_M has the highest fixed-15 total in this category.

Website sensitivity

Cohort-relative sensitivity

The AVX2 measurements are also evaluated with the public website's cohort-relative denominator. These calculations test denominator sensitivity and do not replace the direct profiler result.

Development result

Development experiments

Mac, Docker, GCP, and custom-engine measurements are used to evaluate implementation changes. They are excluded from submission-artifact rankings.

Performance formula definitions

The executable profiler uses S_perf = min(TPS / 15, 1) × 100. The public challenge page defines TPS_max as the fastest qualifying submission. Direct profiler totals use the executable formula. The separate sensitivity calculation uses the website formula. Totals calculated with different formulas are not compared.

Accuracy extraction warning

The pinned profiler's generic score extractor returns the sample count as the score for some generative lm-eval tasks. ARC-Easy uses a separate multiple-choice metric. Generative task results use the project's explicit metric extractor and are excluded from the direct profiler total.

Runtime benchmarks

Controlled runtime baseline

The initial July Docker configuration generated approximately 5.3 tok/s and reached at least 4.77 GB. Concurrency, cache size, and checkpoint count were fixed before subsequent single-variable comparisons.

30 Jul

Baseline

Approximately 5.3 tok/s and at least 4.77 GB. Used for smoke-test comparisons.

31 Jul

Resource caps

Parallel slots 2, four checkpoints, 256 MiB cache: 6.72 tok/s and 4.44 GB.

1 Aug

Native sweep

Six batch and six decode threads, unified KV, two checkpoints: 31.09 tok/s and 3,137 MiB physical footprint.

1 Aug

Bandwidth estimate

31.1 tok/s was 83% of the 37.3 tok/s weight-bandwidth estimate. Additional threads did not increase throughput.

Rejected

Draft-model speculation

A 0.8B draft accepted 98.4% of proposals yet slowed native generation from 30.84 to 24.72 tok/s. Host memory was not reliable in that run, so the rejection rests on measured throughput alone.

Rejected

N-gram speculation

The tested acceptance rate was 12–22%. Lookup and verification overhead exceeded the throughput benefit. The feature remains disabled pending evaluation on representative tutoring traces.

Adopted

Thread cap

Increasing the thread count from six to ten reduced decode throughput to approximately 4.4 tok/s. Temperature was not measured, so the thermal effect of the thread cap is unknown.

Adopted

Unified KV and fewer checkpoints

This configuration reduced retained state and improved prefill without reducing decode throughput.A unified KV cache allocates capacity across active slots instead of reserving a fixed block for each slot. The context budget was set explicitly for subsequent comparisons.

The selected runtime reached 83% of the estimated weight-bandwidth limit. Subsequent optimisation therefore focused on reducing model bytes processed per generated token rather than increasing the thread count.

04

Candidate evaluation

Model-scale and runtime-specific selection

Candidate selection used two evaluations. The first measured reasoning accuracy across model scales. The second measured GGUF artifacts under the scalar participant binary and the portable AVX2 configuration.

Model-scale comparison

On the four-task reasoning set, Qwen3.5 4B averaged 73.3, the 2B model 64.8, and the 0.8B model 51.3. Across college mathematics, high-school mathematics, and college physics, the 4B model exceeded the 2B model by 15.7 points, with a 95% confidence interval of 7.8–23.5. The 4B model was retained as the accuracy baseline for the audit candidates.

Audit candidate comparison

The August audit included Qwen3, Qwen3.5, BitCPM, LFM2.5, MiniCPM5, and Qwen2.5 Math. MiniCPM recorded 0–3% on GSM8K with the evaluated template path. Qwen2.5 Math recorded 24% on ARC-Easy under the audit configuration.A score of 24% is approximately chance performance on a four-choice task. The evaluated bare-GGUF path did not include the model-specific prompt structure. The 1B and 3B BitCPM variants had lower accuracy. The 8B BitCPM variant had higher accuracy but lower scalar-kernel throughput.

Runtime-dependent selection

Pure Q4_0 uses an SSSE3-capable kernel in the scalar audit build. The portable AVX2 backend provides vector kernels for Q4_K_M, Q5_K_M, IQ4_XS, and TQ2_0. Q4_0 has the highest scalar total; Q4_K_M has the highest portable AVX2 total.

05

Quantization and kernel dispatch

Quantization type affects throughput and RSS

A GGUF quantization type determines the stored tensor size and the kernel used by llama.cpp. It can also enable runtime tensor repacking.In the paired campaign, Q4_0 estimated profiler RSS increased from 1,133.1 to 2,049.4 MiB when AVX2 repacking was enabled. Q4_K_M increased from 1,183.5 to 1,989.7 MiB. Q5_K_M and IQ4_XS increased throughput with less than 1 MiB additional RSS. File size alone is therefore insufficient for predicting throughput or peak RSS.

Under the scalar configuration, Q4_0 reached 9.99 tok/s and Q4_K_M reached 5.30 tok/s. Under the portable AVX2 configuration, Q4_K_M reached 15.67 tok/s and scored 80.4484. Q4_0 reached 16.89 tok/s and scored 80.2818 because its estimated repacking RSS was 59.7 MiB higher.

IQ4_XS

File size and runtime conversion

The 4B IQ4_XS accuracy result remained stable, while throughput and resident memory varied with the engine's conversion path. Scored memory must therefore be measured at runtime.

Importance matrix

No reliable gain

The tested imatrix build changed ARC-Easy, GSM8K, college mathematics, and physics results by approximately one or two items in opposing directions. No repeatable accuracy improvement was measured.

Artifact derivation

The scripts in opt/scripts/ reproduce the promoted SHA-256 from a pinned public source file.

mmap is controlled by the evaluator's runtime

The stock Linux audit runtime opens the GGUF with eager page population, so RSS includes file-backed weight pages and runtime buffers. A custom lazy-mmap engine can reduce deployment memory, but mmap policy is not encoded in the submitted GGUF.

Tensor repacking is controlled by the runtime

Disabling repacking reduced one 4B model's development-runtime footprint from approximately 3,236 to 602 MiB. This setting is not encoded in the GGUF and cannot affect the organiser's executable unless that executable exposes the option.

BitCPM4-8B evaluation

Accuracy, throughput, and model-size results

BitCPM4-8B-TQ2_0 recorded 88% on 50 ARC-Easy items, the highest accuracy proxy among the compact candidates. Vocabulary pruning reduced the artifact to approximately 2.2 GB.TQ2_0 represents weights with three values at approximately 2 bits per weight. The scalar binary produced 0.81 tok/s; the portable AVX2 backend produced 7.49 tok/s. AVX2 increased decode throughput by 9.235× and increased the total from 59.1587 to 72.5121. The result remained below the Qwen quantization results above 79 points.

07

Runtime-only memory optimisation

Weight streaming measurements and submission exclusion

The custom engine reduced peak RSS by loading weights from storage during inference. Streaming all weights measured 279 MiB peak RSS and 10.47 tok/s. It did not meet the 15 tok/s threshold, and the required engine changes are not included in a GGUF-only submission.

Properties included in the submitted artifact

Streaming, repacking policy, lazy mmap, thread count, and KV-cache configuration require runtime control. The submitted artifact contains the tensor quantization, tied output head, metadata, and chat template.

Submission constraint

The custom page-cache engine can be used in the Muta application. It is excluded from the competition score because the organiser evaluates the GGUF with its own runtime.

Runtime changes and GGUF changes are evaluated separately. The submitted quantization still interacts with the evaluator's available kernels: Q4_0 has the highest total in the scalar configuration, while Q4_K_M has the highest total in the portable AVX2 configuration.

Effect of AVX2

Every non-Q4_0 artifact recorded higher throughput under AVX2. BitCPM increased from 0.81 to 7.49 tok/s, a factor of 9.235. Its total was 72.5121 because throughput remained below 15 tok/s and estimated profiler RSS was 2,316.4 MiB.

Q4_K_M and Q4_0 both exceed the 15 tok/s performance threshold. Their total-score difference is determined by estimated profiler RSS: Q4_K_M is 59.7 MiB lower. The Q4_K_M decode samples have higher variance than the Q4_0 samples. IQ4_XS records 80.1089, 0.3395 points below Q4_K_M, with 1,082.3 MiB estimated profiler RSS.

Benchmark configuration and evidence limits

Controlled AVX2 proxy llama.cpp b10175 at commit 60bccc3763395e01b039aa1ddeacc8cc0ea69f70; benchmark binary SHA-256 4abfa11a…12fd8. Every model used p512/tg128, -ngl 0, two automatically selected physical-core threads, and five internal samples. RSS is the measured child-tree peak plus the retained 45 MiB profiler-root estimate. Accuracy was reused by immutable GGUF hash. The GCP host has no package-temperature sensor, so thermal remains unknown. These results use the fixed/capped 15 tok/s score; they are neither an official participant-profiler run nor the website-relative sensitivity sweep.
