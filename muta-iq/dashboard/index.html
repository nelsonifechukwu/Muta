Muta technical field report · July–August 2026

Finding the model that survives the laptop

Muta is an offline tutor for maths and scientific reasoning. Its model must fit into 8 GB while retaining enough teaching ability to survive the judge’s speed, memory, heat, and failure checks.

Current model choice — for now

muta-tutor-qwen3-1.7b-q4_0.gguf

A pure Q4_0 Qwen3 1.7B build with tied output weights. It leads the four-model direct profiler campaign by 0.92 points, while remaining close enough to the 0.8B runner-up that a larger accuracy sample or the physical target laptop could reverse the order.

01

The judging problem

Four terms, one constrained machine

The challenge evaluates a GGUF model through llama.cpp on an Ubuntu laptop with four CPU cores, 8 GB of RAM, no discrete GPU, and a 7 GB memory ceiling. A fast model can still lose on tutoring quality. A capable model can still lose on memory or throughput. A crash, out-of-memory event, or illegal instruction is worse than a low score: it disqualifies the run.

Decision rule

On this score, spending 1 GB of memory must buy at least 1.43 tok/s or 5.7 accuracy points just to break even. That exchange rate turned “bigger is better” into a testable claim.

Evidence rules

Four lanes that must not be blended

The project contains measurements from several machines, binaries, and score interpretations. They answer different questions. Every result in this report carries a provenance label so a fast Mac run cannot quietly become an official laptop claim.

Official profiler result

Direct measurement

A full participant run from the official executable. Throughput and root-plus-child peak RSS are measured. This is the current selection surface.

Profiler-parity estimate

Controlled reconstruction

The same no-AVX engine regime, with interleaved timing. Throughput is measured; profiler-root RSS is estimated from a documented 45 MiB offset.

Website sensitivity

Alternative scoring

AVX2 deployment measurements rescored with the public website’s cohort-relative denominator. This tests whether the winner depends on an unknown field.

Development result

Engineering evidence

Mac, Docker, GCP, or custom-engine work used to accept or reject an idea. Useful for causality; not comparable to the direct campaign table.

Why are there two performance formulas?

The executable profiler fixes the speed reference at 15 tok/s: S_perf = min(TPS / 15, 1) × 100. The public challenge page describes a cohort-relative denominator, where TPS_max is the fastest qualifying submission. We use the executable formula for the direct campaign and keep the website formula only as a labelled sensitivity sweep. Combining the two would manufacture precision.

Accuracy extraction warning

The pinned profiler’s generic score extractor returns the sample count as the score for some generative lm-eval tasks. ARC-Easy uses a different, valid multiple-choice metric. Generative results in this report come from the project’s explicit metric extractor and never enter the direct profiler total.

Runtime baseline

First make the system measurable

The first July build could answer questions, but it was not a stable benchmark. Under Docker on the development machine it generated about 5.3 tok/s while memory climbed toward 4.77 GB. Before comparing models, we capped concurrency, cache, and checkpoints; then we measured one change at a time.

30 Jul

Baseline

≈5.3 tok/s, 4.77 GB and rising. Useful as a smoke test, not a scoring result.

31 Jul

Resource caps

Parallel slots 2, four checkpoints, 256 MiB cache: 6.72 tok/s and 4.44 GB.

1 Aug

Native sweep

Six batch and six decode threads, unified KV, two checkpoints: 31.09 tok/s and 3,137 MiB physical footprint.

1 Aug

Bandwidth check

31.1 tok/s was 83% of the 37.3 tok/s weight-bandwidth ceiling. The next useful lever was model bytes, not another thread.

Rejected

Draft-model speculation

A 0.8B draft accepted 98.4% of proposals yet slowed native generation from 30.84 to 24.72 tok/s. Host memory was not reliable in that run, so the rejection rests on measured throughput, not an inferred RAM cost.

Rejected

N-gram speculation

Zero-cost in model memory, but the tested acceptance rate of 12–22% did not pay for the extra work. The feature stays off by default until a tutoring trace gives it enough repeated text.

Adopted

Thread cap

Ten threads collapsed decode to about 4.4 tok/s. Six saturated useful bandwidth without spending more power on contention. The cap is also protection against the thermal cliff.

Adopted

Unified KV and fewer checkpoints

The winning runtime reduced retained state and improved prefill without giving up decode. The context budget became explicit instead of being left to defaults.

04

Model funnel

Capability first, then audit fit

The search narrowed twice. The first pass asked how much scientific reasoning disappeared below four billion parameters. The second asked a stranger but more important question: which tensor layout runs well when the official binary disables native CPU features?

The first narrowing: quality by scale

On a four-task reasoning set, Qwen3.5 4B averaged 73.3, the 2B model 64.8, and the 0.8B model 51.3. The difference grew on college maths, high-school maths, and college physics: 4B led 2B by 15.7 points with a 95% confidence interval of 7.8–23.5. That result justified a 4B baseline before the official kernel regime changed the cost side of the equation.

The second narrowing: nine audit candidates

The August audit included Qwen3 and Qwen3.5 models, BitCPM ternary models, LFM2.5, MiniCPM5, and Qwen2.5 Math. Several nominally attractive files failed for concrete reasons: MiniCPM’s template path reduced GSM8K to 0–3%; Qwen2.5 Math collapsed under the audit configuration; the 1B and 3B ternary variants were compact but weak; and the 8B ternary model was accurate but slow in the generic kernel.

Why the 1.7B model moved ahead

Pure Q4_0 routes every matrix through an SSSE3-capable kernel in the no-AVX audit build. Tying the output head removes a duplicated weight matrix and saved about 175 MB in the final control comparison. Those two properties moved this exact artifact ahead.

05

GGUF and quantisation

File size is not the same as scored memory

Quantisation decides more than bits per weight. It selects kernels, changes whether the engine repacks tensors, and can make a smaller file occupy more RSS. Because the submission is a GGUF artifact rather than a custom runtime, only effects encoded in that file can reach the judge.

Q4_K_M

Strong default, wrong audit path

A good general-purpose compromise under AVX2. In the no-AVX binary, its K-quant matrices fell onto slower generic work than pure Q4_0.

Q4_0

Older format, useful kernel

Slightly blunt as a quantiser, but consistently supported by the audit CPU path. For Qwen3 1.7B, that systems property outweighed the usual format preference.

IQ4_XS

Compact file, possible repack

The 4B IQ4_XS file kept good reasoning scores, yet throughput and resident memory depended on the engine’s conversion path. File bytes alone were a poor proxy.

Importance matrix

No reliable gain

The tested imatrix build moved ARC-Easy, GSM8K, college maths, and physics by roughly one or two items in opposing directions. We found no repeatable accuracy improvement.

Why mmap cannot solve the judged RSS problem

The stock Linux audit runtime opens the GGUF with eager page population. Its RSS therefore includes file-backed weight pages plus runtime buffers. A custom lazy-mmap engine can reduce product memory, but we submit only the GGUF. The file cannot tell the judge’s executable to change its mmap policy. For the competition path, mmap is an engine decision outside the artifact boundary.

Why “no repack” remains a product result

On the development runtime, avoiding repack cut one 4B model’s native footprint from roughly 3,236 to 602 MiB. That is valuable for Muta as software. It is not a legal model-only optimisation unless the official executable exposes the same choice, so it does not enter the campaign score.

06

The ternary branch

An accurate 8B model that taught us where not to cut

BitCPM4-8B-TQ2_0 was the most accurate compact candidate: 88% on the 50-item ARC-Easy proxy. Its ternary body fit in about 2.2 GB after vocabulary pruning. It still generated only 0.81 tok/s in the direct no-AVX run, so accuracy could not recover the performance term.

01

Prune the vocabulary

73,448 tokens became 44,416, padded to a multiple of 64. The file lost 164 MB. English tokenisation stayed identical across 20,464 checked tokens; perplexity moved from 10.558 to 10.473.

Kept
02

Try TQ1_0

The body lost another 340 MB, but generic CPU throughput fell from 3.70 to 2.88 tok/s. Fewer bits did not mean fewer instructions.

Rejected
03

Compress the head

Head and embedding requants saved at most 48 MB. The best score gain was about 0.14 points, too small for the added behavioural risk.

Rejected
04

Factor or sparsify

The ternary matrices were full-rank; rank-2048 factorisation error was about 0.80 before quantisation. Dense GGUF also stores and multiplies zeros, so unstructured sparsity saved no scored work.

Rejected

The branch remains useful. It established that vocabulary pruning can be lossless when validated at the token level, and that exotic compression only helps when the evaluator has a matching kernel.

07

Weight streaming

Memory saved, score lost

Weight streaming was the most direct attempt to trade SSD bandwidth for RAM. It worked as an engine feature: the fully streamed model held only about 313 MiB steady. It failed as a competition strategy because storage could not feed enough weights inside a token interval—and the custom engine cannot be submitted with a GGUF-only entry.

19 August campaign

The first direct profiler decision

Four exact artifacts completed full participant runs on the GCP proxy. Qwen3 1.7B Q4_0 won because it paired a 72% accuracy proxy with nearly the same no-AVX speed as the 0.8B model. The 4B Qwen was more accurate at 76% but generated only 1.13 tok/s. BitCPM led accuracy at 88% but fell to 0.81 tok/s. Neither repaid its speed cost under the fixed-15 formula.

How sensitive is that answer?

The direct campaign uses the executable’s 15 tok/s cap. The public webpage describes performance relative to the fastest cohort model. We therefore rescored the AVX2 deployment measurements at several possible cohort floors. This does not revise the official result; it shows where the choice would change if the public formula governed.

What could change the current choice?

The 0.92-point lead is smaller than the uncertainty implied by 50 accuracy questions. The next decisive tests are a larger, tutoring-aware accuracy evaluation and a full run on the physical target with package temperature. Either test could legitimately reorder the candidates because the present choice is conditional on the measurements we have.
