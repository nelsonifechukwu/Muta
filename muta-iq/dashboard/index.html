01

Competition constraints

Evaluation targets a $150–$500 CPU laptop

The Africa Deep Tech Challenge evaluates language models entirely on-device on a specified standard laptop, without cloud inference. Its seven tracks include Math & Scientific Reasoning, which Muta addresses through offline explanation, worked examples, and quantitative question answering.

The target is an Intel Core i5, 10th to 12th generation, with integrated graphics, Ubuntu 22.04, and a 7 GB RAM limit. Exceeding that limit disqualifies the run. The evaluator accepts GGUF weights through llama.cpp. The base model must be open and may be quantized or fine-tuned, but the submission cannot require another runtime.We disable AVX-512 in our own build and check the disassembly because several eligible consumer CPUs do not support it. An illegal instruction disqualifies the run.

Accuracy contributes half of the total. Performance is capped at 15 tok/s, and efficiency reaches zero at 7 GB, so gains beyond those limits do not increase the profiler score.S_perf = min(TPS/15, 1) × 100 and S_eff = max(0, (7 GB − RSS)/7 GB) × 100. The public challenge page instead defines performance relative to the fastest submission, TPS_max. We use the executable profiler's fixed formula for the primary result and report the cohort-relative formula separately. This gives the following decision threshold:

Decision rule

An additional 1 GB of RSS has to buy 1.43 tok/s or 5.7 accuracy points to break even. We reject a method when its measured return does not meet that threshold.

Why we keep five separate evidence categories on this page

Our numbers come from different systems, CPU features, and performance formulas, so we never blend them into one ranking: official profiler results (the participant executable's own runs), profiler-parity estimates (the scalar reconstruction with a 45 MiB profiler-root allowance we estimated, not measured), controlled vector proxies (paired scalar and vector benchmarks on the same host), website sensitivity (the cohort-relative formula as a separate check, never averaged in), and development results (Mac, Docker, and custom-engine tests that guided decisions but never ranked a submission). Each figure identifies its evidence category by colour and label.

02

Initial scale study

Model scale improves accuracy and increases cost

Before quantization, we compared Qwen3.5 0.8B, 2B, and 4B on four reasoning tasks. This established the accuracy gain from scale that later memory and throughput changes had to offset.

The 4B model exceeded the 2B and 0.8B models on every task. The score adds 0.50 points per accuracy point but only 2.86 points per gigabyte saved, which favours scale until memory and throughput costs dominate. We therefore tested two model strategies under the same 7 GB limit:

Dense strategy

Small dense Qwen models

Quantize the Qwen3/3.5 family aggressively, then compare model scale, tensor precision, and embedded behaviour.

Ternary strategy

Larger low-bit BitCPM model

Compress and prune an 8B BitCPM4 model in TQ2_0 to test whether higher accuracy offsets slower kernels and a larger memory footprint.

Each additional 100 MB reduces the efficiency term by about 0.28 total points. The ternary candidate therefore had to justify a 2.1 GB file through higher accuracy or throughput. Both strategies remain in the tables because their measured trade-offs inform the final selection.

03

Method overview

Nine evaluated optimization methods

We then evaluated nine methods that can change file size, peak RSS, generation speed, or response quality. Each method is retained only when its measured score contribution is positive and its artifact remains compatible with the evaluator.

1

Quantization

Not just bits per weight, but which quantization type the evaluator can run efficiently.

2

Parameter deduplication

Dropping the duplicated output head when embedding and head can share one matrix.

3

Vocabulary pruning

Removing tokens the tutor will never emit, and checking token by token that nothing else changed.

4

Weight streaming

Reading weights from disk instead of keeping the complete file resident.

5

Runtime tuning

Controlling threads, KV cache, checkpoints, and two forms of speculative decoding.

6

CPU execution mode

Testing how scalar and vector execution change throughput, memory, and the quantization ranking.

7

Expanded model search

Testing nine additional candidates and a specialist fine-tune after the initial roster stopped improving.

8

Embedded behaviour

Storing the persona, chat template, and sampling defaults in the GGUF used by judges.

9

Engine-only configuration

Separating repacking, mmap policy, and thread count from changes that the submitted GGUF can carry.

The first five methods modify the GGUF directly. The sixth tests how CPU execution changes their ranking. The seventh and eighth expand or train the model set. The ninth separates model-file changes from engine-only changes. Quantization comes first because it affects every candidate.

04

Method one

Quantization: the file format is the kernel choice

Quantization stores each weight in fewer bits than its training precision, reducing file size at a possible accuracy cost. GGUF supports plain 4-bit rounding (Q4_0), k-quants (Q4_K_M, Q5_K_M), sub-4-bit i-quants, and ternary formats. Their value depends on both tensor precision and the evaluator's available kernels.

We inspected the profiler runtime's kernel source and found that only Q4_0 has a hand-written SIMD path in its scalar-configured build. The other tested formats, including k-quants, fall back to generic C. On the Qwen3 1.7B control, Q4_0 generated 9.99 tok/s against 5.30 tok/s for Q4_K_M. The same pattern appears on the later submission candidate at 12.63 tok/s. This made pure Q4_0 the preferred format for the supplied profiler, pending the separate vector comparison below.

Independent control

The Math-Expert sweep repeated this result across eight quantization layouts of one source model. The expanded-search section reports that control.

05

Method two

Cutting the duplicate head

Many transformer architectures give the embedding table and output head separate matrices of the same shape. When the architecture supports tied embeddings, the output head can reuse the embedding matrix, reducing file size without retraining.

We reproduced the recommended file from its source quant and ran an isolated tied-versus-untied comparison. Removing the duplicate saved about 175 MB, with identical ARC-Easy accuracy in both conditions. We retained this change for compatible candidates.

A separate metadata pass stores the tutor persona, chat template, and sampling defaults without changing tensor bytes. The embedded-behaviour section evaluates that change.

06

Method three

Vocabulary pruning reduces size but does not rescue ternary throughput

Vocabulary pruning removes unused tokens from the embedding table. We applied it to the 8B ternary BitCPM4 model because an English tutor did not require most of its 73,448-token multilingual vocabulary.

01

Vocabulary pruning

We cut the vocabulary from 73,448 to 44,416 tokens and padded it to a multiple of 64, which shrank the file by 164 MB. English tokenisation matched across 20,464 checked tokens; perplexity fell from 10.558 to 10.473.

Kept
02

TQ1_0 body test

The body shrank by 340 MB, but generic CPU throughput fell from 3.70 to 2.88 tok/s. The lower bit width bought us nothing on the evaluated kernel's instruction cost.

Rejected
03

Head and embedding quantization

Head and embedding requantization saved at most 48 MB. The largest estimated total-score gain we found was about 0.14 points, too small to matter.

Rejected
04

Factorisation and sparsity tests

The ternary matrices were full-rank: rank-2048 factorisation error was about 0.80 before quantization. Dense GGUF storage and kernels do not compress or skip unstructured zeros, so sparsity produced no saving.

Rejected

The vocabulary prune was the only retained change. BitCPM4-8B-TQ2_0 still had the highest measured ARC-Easy accuracy at 88%, but generated only 0.81 tok/s on the scalar path. The vector build raised generation to 7.49 tok/s and its total to 72.5121, still below the leading dense Qwen variants. We therefore retained BitCPM as an accuracy reference and removed it from the submission shortlist.

07

Method four

Weight streaming, and where the submission boundary sits

If a model is too large to remain in RAM, its weights can be read from disk as each layer runs. We tested a residency-window streaming engine on the 2.2 GB BitCPM model.

Full streaming reduced peak RSS to 279 MiB but generated only 10.47 tok/s, below the 15 tok/s threshold. At batch size 1, each decoded token reads almost every model weight, so throughput is approximately effective bandwidth divided by model size:A rate of 20 tok/s would require about 44 GB/s of effective bandwidth. The fully resident configuration reached about 41 GB/s and 18.70 tok/s on this host.

Working that ratio backward from each point in the chart above shows the same climb in different units: Stream all backs out to about 23 GB/s of effective bandwidth, Pin 1,500 MB to about 34 GB/s, Resident to about 41 GB/s. The 33 GB/s the target needs falls right at the 1,500 MB pin, where the measured rate, 15.35 tok/s, is the only point in the sweep that clears the line.

Streaming requires a custom engine, while the competition evaluates the submitted GGUF through the organiser's unmodified llama.cpp. An engine change therefore cannot accompany the submitted model:

Submission constraint

Muta's product runtime can use streaming and disabled repacking. Neither change enters the competition score because the organiser evaluates only the GGUF in its runtime.

08

Method five

Runtime standardization for model comparison

Model comparisons require a fixed runtime. We held threads, KV cache, and checkpoints constant, then tested two forms of speculative decoding under the same configuration.

Rejected

Draft-model speculation

Acceptance reached 98.4%, but generation still fell from 30.84 to 24.72 tok/s.

Rejected

N-gram speculation

Acceptance ran only 12–22%, so lookup and verification overhead outweighed the gain.

Adopted

Six-thread cap

Raising the thread count to ten cut decode to about 4.4 tok/s. We had no temperature reading to explain why.

Adopted

Unified KV, two checkpoints

This configuration cut retained state and sped up prefill without slowing decode.Unified KV shares capacity across active slots instead of reserving a fixed block per slot.

Six threads and unified KV reached 31.09 tok/s at 3,137 MiB, 83% of the estimated weight-bandwidth ceiling, on the development host. These engine settings do not accompany the submitted GGUF and are excluded from the model score. Their purpose here is to make the development comparisons repeatable.

Method six

CPU execution mode changes the model ranking

The supplied profiler disables AVX, AVX2, FMA, and F16C. We call this the scalar configuration because the tested k-quant, i-quant, and ternary kernels use generic scalar, or SISD, code there; Q4_0 is the exception and still uses SSSE3 SIMD. The second build enables AVX2, FMA, and F16C, allowing one instruction to process several numeric lanes. We call that the vector configuration. Neither configuration adds threads: both use the same two physical cores. The paired comparison covers fifteen models.

Scalar configurationvector extensions disabled Vector configurationportable SIMD enabled Both configurationstwo physical-core threads

The vector path changed both throughput and ranking. In the 50-question screen, Q4_K_M first moved ahead of pure Q4_0 in the Qwen3 1.7B pair, and Qwen2.5 1.5B then reached 82.8697. Its 500-question accuracy was 71.8%, reducing the vector total to 80.7697 but leaving it 3.9593 points above the current Qwen3.5 candidate on the same sample size. The 3B Q4 candidates remained slower and less efficient.

Method eight

Embedding tutor behaviour in the GGUF

The model-only evaluation loads the GGUF without Muta's application prompt. The tutoring persona, chat template, and sampling defaults must therefore be stored in the model metadata.

The ChatML template inserts the Muta tutoring persona when the client supplies no system turn. It opens the assistant turn with an empty <think></think> block to suppress hidden reasoning. With unrestricted thinking, both tested finalists used the complete 256-token allowance without returning a visible answer. The non-thinking template produced visible answers. The GGUF also stores temperature 0.4, top-p 0.9, min-p 0.05, and repeat penalty 1.05. The persona adds about 130 prompt tokens.

We verified the template with llama.cpp's Jinja engine and llama-cpp-python's separate jinja2 path. Both inserted the persona and returned finish_reason: stop on the accepted prompts. Neither finalist produced a satisfactory proof that √2 is irrational, and some responses reached the 256-token limit. This remains a measured quality limitation.

Current evidence

The larger sample confirms a runtime-dependent split

Qwen2.5 1.5B scores 71.8% on the 500-question ARC-Easy run. With the measured vector throughput and RSS, its total is 80.7697, compared with 76.8104 for Qwen3.5 0.8B. Under the scalar configuration, the corresponding totals are 63.8176 and 72.7895. The preferred model therefore depends on the audit CPU configuration.

Required validation

The larger accuracy run is complete. Qwen2.5 1.5B still needs the physical-target procedure and the same embedded tutor-template and live-prompt checks applied to the current Qwen3.5 file. The physical run must record repeated throughput, whole-tree RSS, temperature, and throttling.

Submission decision

We recommend submitting Muta-Tutor-Qwen3.5-0.8B-Q4_0-final.gguf under the supplied profiler configuration. Qwen2.5 1.5B Q4_K_M is the validated vector candidate. It should replace Qwen3.5 only if the final audit is confirmed to use the vector configuration and the embedded tutor checks pass.

The result is conditional on the runtime. Scalar profiling still favours the files with an efficient scalar path. The vector path favours Q4_K_M and moves the best measured balance to a 1.5B model. The report therefore keeps the direct profiler, scalar screen, and vector proxy separate.
