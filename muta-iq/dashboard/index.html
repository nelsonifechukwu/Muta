Muta technical field report · July–August 2026

Finding the model that survives the laptop

Muta is an offline tutor for maths and scientific reasoning. We need one model to fit an 8 GB classroom laptop, respond at a useful pace, and teach well enough to justify every byte it occupies. This report follows the experiments that brought us to our current answer.

Current model choice

muta-tutor-qwen3-1.7b-q4_0.gguf

For now, we choose a pure Q4_0 Qwen3 1.7B build with tied output weights. It leads the four-model direct profiler campaign by 0.92 points. That lead is narrower than the uncertainty in a 50-question accuracy sample, so a larger evaluation or a run on the physical laptop could reverse the order.

01

What the score rewards

Four terms, and one way to score zero

The competition defines the best model on one concrete machine. It runs a single GGUF through llama.cpp on an Ubuntu laptop with four CPU cores, 8 GB of RAM, no discrete GPU, and a 7 GB memory ceiling. Accuracy, speed, and memory all matter; a crash, an out-of-memory kill, or an illegal instruction reduces the entire run to zero.The engine build therefore pins GGML_AVX512=OFF, and the Dockerfile greps the disassembly for AVX-512 mnemonics. Much of the target field, including Zen 3 and 12th-generation consumer Intel, faults on AVX-512.

Two terms stop paying after a threshold.S_perf = min(TPS/15, 1) × 100 and S_eff = max(0, (7 GB − RSS)/7 GB) × 100. Past 15 tok/s, speed stops paying. Speed earns nothing beyond 15 tok/s, and none of our candidates approached the 7 GB memory ceiling. Accuracy has no such cap, and it carries half the score. We could therefore spend memory on capability, but only up to a calculable break-even point.

Decision rule

Spending 1 GB of memory has to buy at least 1.43 tok/s or 5.7 accuracy points to break even. This exchange rate became our first filter. Before applying it, however, we had to decide which measurements could be compared at all.

How we treat evidence

Four lanes that must not be blended

Our measurements span different machines, binaries, and interpretations of the score. They answer different questions. We therefore keep four evidence lanes, so a useful Mac experiment cannot drift into the report as an official-profiler result.

Official profiler result

Direct measurement

A full participant run from the official executable. It measures throughput and root-plus-child peak RSS. These are the runs we use to choose the current model.

Profiler-parity estimate

Controlled reconstruction

A controlled reconstruction of the same no-AVX engine regime. We measure throughput in timed samples and estimate profiler-root RSS from a documented 45 MiB offset.The profiler's root process holds the Python interpreter and lm-eval imports on top of the llama-bench child. Across paired runs that overhead sat at 45 MiB, stable enough to add as a constant but not a substitute for measuring it.

Website sensitivity

Alternative scoring

AVX2 deployment measurements rescored with the public website's cohort-relative denominator. This lane asks whether an unknown field could change the winner; it does not revise the direct result.

Development result

Engineering evidence

Mac, Docker, GCP, or custom-engine work used to accept or reject an idea. These experiments explain how we reached the campaign, but they do not rank its artifacts.

Why are there two performance formulas?

The executable profiler fixes the speed reference at 15 tok/s: S_perf = min(TPS / 15, 1) × 100. The public challenge page describes a cohort-relative denominator, where TPS_max is the fastest qualifying submission. We use the executable formula for the direct campaign and the website formula for a labelled sensitivity sweep. Mixing them would manufacture precision neither one has.

Accuracy extraction warning

The pinned profiler's generic score extractor returns the sample count as the score for some generative lm-eval tasks. ARC-Easy uses a different, valid multiple-choice metric. Generative results in this report come from the project's explicit metric extractor and never enter the direct profiler total.

03

Making Muta measurable

First, give every change a baseline

The first July build could answer questions, but it could not yet support a trustworthy comparison. Under Docker on the development machine, it generated about 5.3 tok/s while memory climbed toward 4.77 GB. We first bounded concurrency, cache, and checkpoints; only then did we change one variable at a time.

30 Jul

Baseline

≈5.3 tok/s, 4.77 GB and rising. We kept it as a smoke-test baseline.

31 Jul

Resource caps

Parallel slots 2, four checkpoints, 256 MiB cache: 6.72 tok/s and 4.44 GB.

1 Aug

Native sweep

Six batch and six decode threads, unified KV, two checkpoints: 31.09 tok/s and 3,137 MiB physical footprint.

1 Aug

Bandwidth check

31.1 tok/s reached 83% of the 37.3 tok/s weight-bandwidth ceiling. More threads were no longer the answer, so we turned to the bytes moved for each token.

Rejected

Draft-model speculation

A 0.8B draft accepted 98.4% of proposals yet slowed native generation from 30.84 to 24.72 tok/s. Host memory was not reliable in that run, so the rejection rests on measured throughput alone.

Rejected

N-gram speculation

Zero cost in model memory, but the tested acceptance rate of 12–22% did not pay for the extra work. The feature stays off until a tutoring trace gives it enough repeated text.

Adopted

Thread cap

Ten threads collapsed decode to about 4.4 tok/s. Six saturated useful bandwidth without more contention. Temperature was not measured in this sweep, so the cap's thermal effect remains unverified.

Adopted

Unified KV and fewer checkpoints

The winning runtime retained less state and prefilled faster without giving up decode.A unified KV cache lets all slots draw from one pool instead of reserving a fixed block each, so an idle slot no longer holds memory a busy one needs. We made the context budget explicit instead of leaving it to defaults.

The runtime sweep removed the easiest waste and exposed the real constraint: autoregressive decode was already close to the host's memory-bandwidth limit. From that point on, the model itself had to do less work per token. Another thread or cache flag would not be enough.

04

Narrowing the field

Capability first, then audit fit

We narrowed the field twice, for two different reasons. First we asked how much scientific reasoning disappeared below four billion parameters. Then the audit binary changed the practical question: which tensor layout still ran well after the CPU features we had been building for were switched off?

First narrowing by model scale

On a four-task reasoning set, Qwen3.5 4B averaged 73.3, the 2B model 64.8, and the 0.8B model 51.3. The gap widened on college maths, high-school maths, and college physics: 4B led 2B by 15.7 points, 95% CI 7.8–23.5. We therefore carried a 4B baseline into the audit. The audit, in turn, changed the cost side of the equation.

Second narrowing across nine audit candidates

The August audit covered Qwen3 and Qwen3.5 models, BitCPM ternary models, LFM2.5, MiniCPM5, and Qwen2.5 Math. Several candidates that looked plausible on paper failed in the judging path. MiniCPM's template path dropped GSM8K to 0–3%. Qwen2.5 Math collapsed under the audit configuration.A maths-specialised 1.5B scoring 24% on ARC-Easy is at chance for a four-choice task. The model expects its own prompt scaffolding, which the bare-GGUF judging path does not supply. The 1B and 3B ternary variants were compact but weak, while the 8B ternary model was accurate but slow in the generic kernel.

Why the 1.7B model moved ahead

Pure Q4_0 routes every matrix through an SSSE3-capable kernel in the no-AVX audit build. Tying the output head removes a duplicated weight matrix and saved about 175 MB in the final control comparison. The winner emerged from that combination of layout and architecture, not from parameter count alone.

05

When file size misleads

A GGUF chooses its kernel too

A quantisation label appears to describe file size. In practice, it also selects a kernel and can decide whether the engine repacks tensors.Repacking rewrites quantised weights into a layout a specific SIMD path prefers. It is fast, and it costs a second full-size copy of the weights in RSS. The audit image does not repack; Homebrew's ARM build does. The same file therefore reports 1,133 MiB in one and 2,029 MiB in the other. A smaller file can therefore occupy more resident memory or run much more slowly. Since we submit a GGUF rather than a runtime, only properties encoded in that file reach the judge.

That dispatch decision explains an otherwise surprising choice. We shipped pure Q4_0 rather than the Q4_K_M we would normally prefer for a laptop deployment. In the source GGUF, the Q6_K head and three imatrix-induced Q4_1 layers would have sent about a quarter of the bytes through scalar C.

IQ4_XS

Compact file, possible repack

The 4B IQ4_XS file retained its reasoning scores, yet throughput and resident memory depended on the engine's conversion path. File bytes alone were a poor proxy for scored memory.

Importance matrix

No reliable gain

The tested imatrix build moved ARC-Easy, GSM8K, college maths, and physics by roughly one or two items in opposing directions. No repeatable accuracy improvement.

How the artifact was derived

Every step below is scripted in opt/scripts/ and reproduces the promoted SHA-256 from a pinned public source file.

Why mmap cannot solve the judged RSS problem

The stock Linux audit runtime opens the GGUF with eager page population, so its RSS includes file-backed weight pages plus runtime buffers. A custom lazy-mmap engine can reduce product memory, but we submit only the GGUF, and the file cannot tell the judge's executable to change its mmap policy. For the competition path, mmap sits outside the artifact boundary.

Why "no repack" remains a product result

On the development runtime, avoiding repack cut one 4B model's native footprint from roughly 3,236 to 602 MiB. Muta's deployment can use that saving. The campaign cannot unless the official executable exposes the same choice.

06

The ternary branch

An accurate 8B model that taught us where not to cut

BitCPM4-8B-TQ2_0 gave us the strongest accuracy proxy among the compact candidates: 88% on 50 ARC-Easy items. After vocabulary pruning, its ternary body fit in about 2.2 GB.TQ2_0 stores each weight as one of three values in roughly 2 bits, so an 8B model reaches the file size of a 2B k-quant. On hardware with a matching kernel it is fast. The audit binary has no such kernel. Yet the direct no-AVX run produced only 0.81 tok/s. Accuracy could not buy back that much lost performance.

01

73,448 tokens became 44,416, padded to a multiple of 64. The file lost 164 MB. English tokenisation stayed identical across 20,464 checked tokens; perplexity moved from 10.558 to 10.473.

The body lost another 340 MB, but generic CPU throughput fell from 3.70 to 2.88 tok/s. Fewer bits did not mean fewer instructions.

03

Compress the head

Head and embedding requants saved at most 48 MB. The best score gain was about 0.14 points, too small for the added behavioural risk.

Rejected
04

Factor or sparsify

The ternary matrices were full-rank; rank-2048 factorisation error was about 0.80 before quantisation. Dense GGUF also stores and multiplies zeros, so unstructured sparsity saved no scored work.

Rejected

We kept the vocabulary-pruning method because it survived token-level validation. We rejected the submission candidate because compression without a matching evaluator kernel saved bytes but not scored work.

07

The submission boundary

Weight streaming saved memory, not score

Weight streaming made the intended trade: SSD bandwidth for RAM. In the profiler-style sweep, streaming every weight cut peak RSS to 279 MiB at 10.47 tok/s. As a competition strategy, it still failed twice. Storage could not feed enough weights inside one token interval, and the custom engine could not accompany a GGUF-only entry.

The budget control assumes 48 ms of compute per token.Measured on the development host for the 2.2 GB ternary model. At 15 tok/s a token lasts 66.7 ms, which leaves 18.7 ms of slack: about 25 MB at 1.35 GB/s, or 1.1% of the model. At the target rate and a typical SSD, the disk can deliver roughly one percent of the model per token. Streaming becomes useful only after the working set is already small.

What actually reaches the judge

Streaming, no-repack, and lazy mmap require engine control. The judge receives only a GGUF, so none of them can change the scored run.

Submission boundary

The custom page-cache engine stays in the offline product. It is excluded from the submission argument because the challenge asks for a GGUF model evaluated by the organiser's runtime.

This boundary separated two kinds of progress. The custom engine remains valuable to the Muta product, but only the changes inside the GGUF could enter the campaign. We therefore took the pure-Q4_0 layout, tied head, and embedded behaviour into the direct profiler—and left the rest outside the score.

The direct campaign

Four artifacts, one narrow lead

Four exact artifacts completed full participant runs on the GCP proxy. Qwen3 1.7B Q4_0 paired a 72% accuracy proxy with almost the same no-AVX speed as the 0.8B model, and that balance gave it the lead. The 4B Qwen reached 76% but generated 1.13 tok/s; BitCPM reached 88% but fell to 0.81 tok/s. Under the fixed-15 formula, neither larger model repaid its speed cost.

Sensitivity to the scoring formula

The executable caps the direct campaign at 15 tok/s, while the public webpage describes performance relative to the fastest model in the cohort. We therefore rescored the separate AVX2 deployment measurements at several possible cohort floors. The direct result does not move; this sweep shows where the public formula would change the choice.

What could change the current choice?

The 0.92-point lead is smaller than the uncertainty implied by 50 accuracy questions.The winner's 72% carries a 58.3–82.5 interval; the runner-up's 68% carries 54.2–79.2. Those overlap almost entirely. Fifty items can separate 72% from 24%, not 72% from 68%. The next decisive tests are a larger, tutoring-aware accuracy evaluation and a full run on the physical target with package temperature. Either result could reorder the candidates.

Current state

A reproducible candidate, with two decisive tests left

We now have an exact GGUF candidate, a pinned audit binary, a direct profiler campaign, and an evidence trail for the ideas that did not survive measurement. That is enough to choose the next model, but not enough to close the project. Two measurements remain decisive.

  1. 01
    Run the exact artifact on the physical competition-class laptop.

    Measure whole-tree RSS, package temperature, throttling, and repeated throughput under the submitted runtime.

  2. 02
    Replace the 50-item proxy with a tutoring-aware accuracy evaluation.

    Test mathematical correctness, explanation quality, calibrated hints, and failure handling. ARC-Easy cannot measure the full 50% term.
