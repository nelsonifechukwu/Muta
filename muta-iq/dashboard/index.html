01

Competition constraints

Evaluation targets a $150–$500 CPU laptop

The Africa Deep Tech Challenge requires a working on-device language-model application with no cloud dependency. Math & Scientific Reasoning is one of seven categories. The model is judged live, so the artifact has to answer through the organiser's runtime rather than through a prepared transcript.

The standard machine has an Intel Core i5 from the 10th to 12th generation, 8 GB DDR4 memory, integrated graphics, and Ubuntu 22.04. The sandbox exposes four CPU cores and enforces a 7 GB peak-RSS ceiling. Exceeding the memory limit, crashing, or failing to run disqualifies the submission. The model must be a GGUF executed by llama.cpp, and it must work offline with zero external network dependency. Quantized and fine-tuned open models are permitted.

The public scoring model assigns 50% to accuracy, 30% to generation speed, and 20% to memory efficiency, with a ten-point thermal penalty above 85°C or when throttling is detected. It also lists a 10% Budget Profile multiplier and a 15% African Language multiplier. Those multipliers are outside this model-ranking calculation because the same application profile surrounds every candidate and no language bonus has been validated. The public page defines performance relative to the fastest submission, while the supplied profiler uses a capped 15 tok/s reference. This report uses the executable profiler formula for its reproducible internal totals and retains the public formula only as a separate sensitivity analysis. ARC-Easy is an internal proxy, not the qualitative score submitted to the judges.

Decision rule

An additional 1 GB of RSS has to buy 1.43 tok/s or 5.7 accuracy points to break even. We reject a method when its measured return does not meet that threshold.

CPU configurations. Scalar configuration: the supplied profiler configuration, with wider vector extensions disabled for the affected kernels. Vector configuration: portable SIMD enabled through AVX2, FMA, and F16C on the same two physical cores. From this point onward, the report uses only “scalar” and “vector.”

Why we keep five separate evidence categories on this page

Our numbers come from different systems and protocols, so we never blend them into one ranking: official profiler results are complete participant-executable runs; profiler-parity estimates reconstruct the supplied scalar configuration; controlled vector proxies pair scalar and vector measurements on one host; website sensitivity applies the public cohort-relative formula separately; and development results guide engineering without ranking a submission. Each figure identifies its evidence category.

04

Optimization method

Quantization: the file format is the kernel choice

Quantization stores each weight in fewer bits than its training precision, reducing file size at a possible accuracy cost. GGUF supports plain 4-bit rounding (Q4_0), k-quants (Q4_K_M, Q5_K_M), sub-4-bit i-quants, and ternary formats. Their value depends on both tensor precision and the evaluator's available kernels.

Protocol. We compared quantizations produced from matched source weights, using the same prompt-processing and generation geometry for throughput and separate retained ARC-Easy runs for accuracy. The Qwen3 1.7B ladder tested Q4_0, Q4_K_M, Q5_K_M, and IQ4_XS; the Math-Expert control added Q4_K_S, Q5_0, TQ formats, and mixed layouts. The quantization sweep kept model identity, task, and runtime fixed within each comparison.

We inspected the profiler runtime's kernel source and found that only Q4_0 has a hand-written SIMD implementation under scalar execution. The other tested formats, including k-quants, fall back to generic C. On the Qwen3 1.7B control, Q4_0 generated 9.99 tok/s against 5.30 tok/s for Q4_K_M. The same pattern appears on the later submission candidate at 12.63 tok/s. This made pure Q4_0 the preferred format for the supplied profiler, pending the vector comparison below.

Independent control

The Math-Expert sweep repeated this result across eight quantization layouts of one source model. The expanded-search section reports that control.

Narrowing. Retain Q4_0 for the supplied scalar profiler and Q4_K_M for the vector candidate field. Reject Gemma 2 Q8_0 as a current contender: its 74% ARC-Easy n=50 result does not compensate for 6.47 tok/s vector decode, 2,871 MiB vector RSS, and a 61.9274 total.

05

Optimization method

Cutting the duplicate head

Many transformer architectures give the embedding table and output head separate matrices of the same shape. When the architecture supports tied embeddings, the output head can reuse the embedding matrix, reducing file size without retraining.

Protocol and result. We reproduced the Qwen3 1.7B candidate from one source quant, changed only whether the embedding and output head shared storage, and repeated ARC-Easy. Removing the duplicate saved about 175 MB, while both artifacts scored 72% on the retained ARC-Easy run. The comparison supports a file-size reduction; it does not establish exact behavioural identity beyond that evaluation.

Narrowing. Retain tied embeddings where the architecture already supports them. Do not attempt deduplication on models whose head and embedding are genuinely distinct. A separate metadata pass stores the tutor persona, chat template, and sampling defaults without changing tensor bytes.

06

Optimization method

Vocabulary pruning reduces size but does not rescue ternary throughput

Vocabulary pruning removes unused tokens from the embedding table. We applied it to the 8B ternary BitCPM4 model because an English tutor did not require most of its 73,448-token multilingual vocabulary.

Protocol. The BitCPM comparison rewrote the vocabulary and embedding rows, then checked 20,464 English tokens for identical tokenization and reran perplexity. Qwen uses a coupled BPE vocabulary and merge table that the available tool could not rewrite safely, so no Qwen vocabulary result is claimed.

07

Optimization method

Weight streaming, and where the submission boundary sits

If a model is too large to remain in RAM, its weights can be read from disk as each layer runs. We tested a residency-window streaming engine on the 2.2 GB BitCPM model.

Protocol. The development engine varied the resident-weight budget while keeping the BitCPM GGUF and decode workload fixed. Peak RSS and generation throughput were measured for full streaming, three pinned budgets, and full residency on the same host.

Full streaming reduced peak RSS to 279 MiB but generated only 10.47 tok/s, below the 15 tok/s threshold. At batch size 1, each decoded token reads almost every model weight, so throughput is approximately effective bandwidth divided by model size:A rate of 20 tok/s would require about 44 GB/s of effective bandwidth. The fully resident configuration reached about 41 GB/s and 18.70 tok/s on this host.

Working that ratio backward from each point in the chart above shows the same climb in different units: Stream all backs out to about 23 GB/s of effective bandwidth, Pin 1,500 MB to about 34 GB/s, Resident to about 41 GB/s. The 33 GB/s the target needs falls right at the 1,500 MB pin, where the measured rate, 15.35 tok/s, is the only point in the sweep that clears the line.

Streaming requires a custom engine, while the competition evaluates the submitted GGUF through the organiser's unmodified llama.cpp. An engine change therefore cannot accompany the submitted model:

Submission constraint

Muta's product runtime can use streaming and disabled repacking. Neither change enters the competition score because the organiser evaluates only the GGUF in its runtime.

Narrowing. Reject streaming as a competition lever because it requires a custom engine and misses the throughput target at its lowest-RSS point. Retain it only as a product fallback for machines that cannot keep the model resident.

08

Optimization method

Runtime standardization for model comparison

Model comparisons require a fixed runtime. We held threads, KV cache, and checkpoints constant, then tested two forms of speculative decoding under the same configuration.

Meaning and score hypothesis. Thread caps determine how many CPU workers contend for memory bandwidth. Speculative decoding proposes several tokens with a smaller draft model or a repeated prompt n-gram, then verifies them with the main model; it helps only when enough proposals are accepted to repay the extra work. Unified KV and explicit checkpoints constrain retained sequence state.

Artifacts and protocol. The thread and KV sweeps used Qwen3.5 4B Q4_K_M with the same prompt battery around a native baseline. Draft speculation paired that target with Qwen3.5 0.8B Q4_K_M; n-gram speculation used repeated prompt text instead of a second model. Each development sweep varied one runtime control at a time. These measurements configure the product; they do not rank GGUF submissions.

Rejected

Draft-model speculation

Acceptance reached 98.4%, but generation still fell from 30.84 to 24.72 tok/s.

Rejected

N-gram speculation

Acceptance ran only 12–22%, so lookup and verification overhead outweighed the gain.

Adopted

Six-thread cap

Raising the thread count to ten cut decode to about 4.4 tok/s. We had no temperature reading to explain why.

Adopted

Unified KV, two checkpoints

This configuration cut retained state and sped up prefill without slowing decode.Unified KV shares capacity across active slots instead of reserving a fixed block per slot.

Narrowing. Six threads and unified KV reached 31.09 tok/s at 3,137 MiB, 83% of the estimated weight-bandwidth ceiling, on the development host. Retain explicit resource caps, reject both speculation modes and excess threads, and keep all of these results outside the GGUF score.

09

Optimization methods

Methods that narrowed the artifact and architecture field

The remaining branches tested whether selective precision, removed structure, smaller architectures, new training, tensor layout, or shorter state could improve the same score. Several produced useful negative results.

GGUF-contained

Mixed tensor or layer quantization

Meaning and score hypothesis. Mixed quantization keeps sensitive tensors at higher precision while compressing the rest of the model. It is useful only if the recovered accuracy repays slower decode and higher RSS.

Artifacts and protocol. The Math-Expert sweep compared a Q4_0 body with Q6_K or Q8_0 tied embeddings, and a Q4_0 body with Q5_0 in the last four blocks plus a Q8_0 embedding. All variants came from one F16 source and used the same scalar/vector throughput and ARC-Easy n=50 protocols.

Result and narrowing. The embedding variants fell from 52% to 50% ARC-Easy while becoming slower and larger. Raising the last four blocks reached 56% but lowered the scalar total by 1.0398. Reject all tested mixed layouts; retain uniform Q4_K_M for Math-Expert and the current Qwen2.5 candidate.

GGUF-contained if supported

Structured and unstructured pruning

Meaning and score hypothesis. Structured pruning removes whole layers or low-rank factors that a dense runtime can skip. Unstructured pruning zeros individual weights and helps only when the file format and kernels compress or skip those zeros.

Artifacts and protocol. A Qwen control removed one layer and repeated throughput and ARC-Easy. The BitCPM branch measured singular-value reconstruction error for its large matrices and checked whether dense GGUF storage could benefit from sparse zeros.

Result and narrowing. Removing one Qwen layer improved speed by about 3.7% but lost two ARC-Easy points. The BitCPM matrices remained full-rank; rank-2048 error was about 0.80 before quantization, and unstructured zeros produced no dense-file or kernel saving. Reject the measured pruning branches.

GGUF-contained

Smaller architectures

Meaning and score hypothesis. A smaller model moves fewer weight bytes per token and usually uses less RSS. It wins only if its capability loss is smaller than the performance and efficiency gain.

Artifacts and protocol. The initial four-task study compared Qwen3.5 at 0.8B, 2B, and 4B. Later staged screens added compact Gemma, LFM, MiniCPM, BitCPM, specialist Qwen derivatives, and the eight models in the current paired experiment.

Result and narrowing. The 0.8B Qwen was too weak in the first reasoning study, while 3B–4B candidates paid too much in throughput and RSS. Promote the 1B–1.5B region for the current vector screen; retain Qwen3.5 0.8B only because its Q4_0 scalar kernel and embedded behaviour make it the safer supplied-profiler artifact.

GGUF-contained after training

Distillation and fine-tuning

Meaning and score hypothesis. Distillation transfers behaviour from a larger teacher into a smaller model; fine-tuning adapts a base model to tutoring or mathematical reasoning. Either can raise accuracy without changing inference size.

Artifacts and protocol. We screened completed public derivatives including Math-Expert, Qwen2.5 Math, NuminaMath, OpenMath-Nemotron, Noema, VibeThinker, and Qwen3.5 Opus. Their retained evidence uses staged accuracy and throughput gates, not one common complete campaign. No new private fine-tune completed a reproducible conversion and benchmark cycle.

Result and narrowing. Math-Expert remains useful as earlier direct-profiler evidence, but its ARC-Easy n=500 result is 54.6%. Other specialists failed an accuracy, throughput, or provenance gate. Defer new distillation or fine-tuning; do not infer a missing result.

Stored layout plus engine-only policy

Tensor layout, alignment, and runtime repacking

Meaning and score hypothesis. GGUF layout determines how tensors are stored; the engine may repack them into a faster in-memory arrangement. Repacking can improve kernels but consume additional RSS.

Artifacts and protocol. A 4B development control compared the default runtime with repacking disabled. We also reviewed custom alignment and packing, but did not create an unsupported GGUF layout because load failure would be disqualifying.

Result and narrowing. Disabling repacking reduced the measured development footprint from about 3,236 to 602 MiB without a clear speed loss. The submitted GGUF cannot select that runtime policy. Retain stock GGUF layout for compatibility and keep no-repack as a product-only setting.

Engine-only

Context size and KV-cache implications

Meaning and score hypothesis. Context length controls how many token states the KV cache may retain. Shorter or quantized caches can reduce memory, but they do not reduce weight traffic during batch-one decode.

Artifacts and protocol. Product sweeps capped slots, context checkpoints, and cache RAM, then tested unified KV. The participant profiler fixes a 512-token prompt and 128 generated tokens, so changing GGUF context metadata does not change the scored workload.

Result and narrowing. Explicit caps stopped development-memory growth and unified KV reduced retained state. Reject context metadata as a profiler optimization; retain bounded context and KV settings only in the product runtime.

Latest architecture screen

Eight models under matched scalar and vector execution

Using the scalar and vector configurations defined above, the final architecture screen measures the same eight GGUFs under two CPU kernel regimes while holding model identity, workload, and core count fixed.

Meaning and score hypothesis. Scalar and vector execution select different implementations of the same tensor operations. Vector kernels process several values per instruction and can raise throughput, but they do not change the GGUF's learned weights or confer a new accuracy result. A candidate benefits only when the throughput gain outweighs any change in measured RSS.

Protocol. All eight GGUFs ran a 512-token prompt and 128-token decode on the same 2C/4T x86 proxy. Each execution lane used five internal timing samples. Peak child-tree RSS received the retained 45 MiB profiler-root estimate. ARC-Easy n=50 was evaluated once per GGUF and reused in both scores. Changing the CPU kernel does not create a new accuracy measurement.

Why accuracy previously appeared to change

The raw screen has one accuracy row per GGUF and two throughput rows per GGUF. The scoring code combines that one accuracy value with scalar or vector throughput and RSS. Apparent accuracy differences elsewhere came from ARC-Easy n=50 versus n=500, different GGUF artifacts, different tasks, or separate evaluation runs—not from vector execution. A CPU-kernel accuracy claim would require a repeated accuracy evaluation and supporting raw evidence.

Qwen2.5 1.5B ranks first in the n=50 vector screen at 82.8697, followed by Qwen2 1.5B at 82.2176. Llama 3.2 1B ranks third at 78.0999 and uses the least vector RSS, 1,397.8 MiB. The higher raw accuracy of Qwen2.5 3B and Phi-4 Mini does not repay their lower throughput and higher memory. Gemma 2 2B Q8_0 reaches 61.9274 and is not competitive.

Optimization method

Embedding tutor behaviour in the GGUF

The model-only evaluation loads the GGUF without Muta's application prompt. The tutoring persona, chat template, and sampling defaults must therefore be stored in the model metadata.

Meaning and score hypothesis. GGUF metadata can define the chat wrapper, a default tutoring instruction, and sampling parameters when the evaluator supplies no application prompt. This does not change the model tensors or profiler throughput, but it can materially affect the qualitative tutoring assessment.

Artifacts and protocol. The final Qwen3.5 file was derived from its source quant by adding only metadata. We compared all 320 tensor payloads, exercised the template through two independent Jinja implementations, and ran a fixed four-prompt tutor-behaviour check with hidden reasoning enabled and disabled.

The ChatML template inserts the Muta tutoring persona when the client supplies no system turn. It opens the assistant turn with an empty <think></think> block to suppress hidden reasoning. With unrestricted thinking, both tested finalists used the complete 256-token allowance without returning a visible answer. The non-thinking template produced visible answers. The GGUF also stores temperature 0.4, top-p 0.9, min-p 0.05, and repeat penalty 1.05. The persona adds about 130 prompt tokens.

We verified the template with llama.cpp's Jinja engine and llama-cpp-python's separate jinja2 path. Both inserted the persona and returned finish_reason: stop on the accepted prompts. Neither finalist produced a satisfactory proof that √2 is irrational, and some responses reached the 256-token limit. This remains a measured quality limitation.

Result and narrowing. Retain the non-thinking ChatML template, tutor persona, and conservative sampling defaults in the submitted GGUF. Do not promote Qwen2.5 to the final artifact until the same tensor-identity, template, and live-prompt checks pass.
