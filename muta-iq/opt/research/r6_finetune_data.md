Researched 2026-08-17 (UTC ~10:00–11:00). Team-muta, ADTC 2026 Laptop LLM track, domain
`math_scientific_reasoning`. Every dataset row below was checked live against the Hugging Face API
(`/api/datasets/<id>`, `datasets-server /size`, `/parquet`, raw file HEADs) or the GitHub API unless
marked *inference* or *unverified*. Licences are what the card/repo says today; several are wrong or
missing (flagged). Nothing on disk was modified except this file.

Context that shapes the plan (from `opt/research/r1_template.md`, `~/.claude/.../memory/*`, and the
installed `adtc_profiler` 0.1.0 source read today):

* **S_acc (50 %) is a judge chatting live with the raw GGUF** (2 our prompts + 2–3 hidden in-domain
  prompts, 0–100 each) through the organisers' llama.cpp b10175 image, **no system prompt from us**
  unless baked into the GGUF chat template. ⇒ Any fine-tune must make the model behave like a tutor
  *with no system prompt* and be robust to default sampling. That is the primary objective of the SFT.
* Only the GGUF file reaches the audit; LoRA adapters kept separate at inference are worthless there.
* The profiler's `accuracy` stage is **lm-evaluation-harness 0.4.12 driven through llama-cpp-python 0.3.34**
  (`adtc_profiler/accuracy.py`: `run_benchmark(model_path, task=..., limit=..., seed=42)`, raw
  completions, no chat template, `n_ctx=2048`). Any lm-eval task name works via
  `--accuracy-task` / `accuracy.run_benchmark(...)`. The env has `datasets 5.0.1` ⇒ script-based hub
  datasets (`math_qa`, `masakhane/afriqa`) **do not load**; parquet/tsv/json ones do.
* Model of record: `openbmb/BitCPM-CANN-8B` (MiniCPM4 arch, ternary QAT, official TQ2_0 GGUF), with 3B/1B
  siblings in `opt/candidates/`. Ternary weights are the S_eff/S_perf lever, so the fine-tuning
  question is really "can we SFT a ternary QAT checkpoint without breaking it" (§3.2).

## 1. Datasets — African secondary-school exam / curriculum

(no licence, no explanations), (ii) the ALOC questions API (free token, MIT code, ~6 k–20 k UTME/WASSCE/NECO
items), and (iii) two **gated (auto-approve)** HF datasets that need a logged-in click. Everything else is PDFs
behind commercial sites. Kenya (KCSE), Ghana, Uganda: PDFs only (teacher.co.ke, freekcsepastpapers.com,

## 5. Fine-tuning recipes

### 5.1 FP 1–4 B instruct models with Unsloth (LoRA/QLoRA), ≤ 5 GPU-h

Sources: Unsloth "LoRA Hyperparameters Guide" https://unsloth.ai/docs/get-started/fine-tuning-llms-guide/lora-hyperparameters-guide ;
Qwen3.5 fine-tune guide https://unsloth.ai/docs/models/qwen3.5/fine-tune ; Qwen3 guide https://unsloth.ai/docs/models/tutorials/qwen3-how-to-run-and-fine-tune ;
saving to GGUF https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-gguf (all fetched today; the older `docs.unsloth.ai/...` URLs 301-redirect).

Recommended settings (verbatim from the hyperparameter guide unless noted):
* learning rate **`2e-4`** ("starting point" for LoRA/QLoRA; RL 5e-6); **"1-3 epochs. For most instruction-based datasets, training for more than 3 epochs offers diminishing returns and increases the risk of overfitting."**
* rank **r = 16 or 32** (choices 8/16/32/64/128); **`lora_alpha = 2 * lora_rank` or `lora_alpha = lora_rank`**; `lora_dropout = 0`; target modules **`q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj`**;
  batch 2 × grad-accum 8 (effective 16); warmup 5–10 % of steps; weight decay 0.01–0.1; scheduler linear or cosine; `use_gradient_checkpointing = "unsloth"`; `use_rslora = False`.
* QLoRA vs LoRA table: QLoRA "4× less (75% reduction)" VRAM, "Marginally less accurate", "Slightly slower".
* Qwen3.5 page: "Please use `transformers v5` for Qwen3.5. Older versions will not work."; bf16 LoRA VRAM "0.8B: 3GB • 2B: 5GB • 4B: 10GB • 9B: 22GB • 27B: 56GB"; example SFT recipe `r = 16, lora_alpha = 16, per_device_train_batch_size = 1, gradient_accumulation_steps = 4, warmup_steps = 10, max_steps = 100, optim = "adamw_8bit", seed = 3407`. Free Colab notebooks exist for 0.8B/2B/4B.
* Qwen3 page: reasoning models — "Use 75% reasoning and 25% non-reasoning in your dataset" (their notebook mixes NVIDIA open-math-reasoning with FineTome); `max_seq_length = 2048` for testing; "Qwen3 (14B) fits comfortably in a Google Colab 16GB VRAM Tesla T4 GPU" (QLoRA).
* Third-party datapoint for time budgeting (github.com/youssif00/Unsloth-Llama3-Finetune, *not verified by us*): Llama-3.2-3B QLoRA on a **T4**, bs 2 × ga 4, 60 steps on FineTome ≈ **12 min** ⇒ ~0.7 samples/s ⇒ **1 epoch of 5 k samples ≈ 2 h on T4**; an A100 is roughly 5–6× faster (*inference*) ⇒ ~20–25 min. Plan T4 runs at ≤ 5 k samples × 1 epoch, `max_seq_length ≤ 1024`, `packing=True`; A100 allows 10–15 k × 2 epochs inside 5 GPU-h including export.
* Data format: ChatML/`apply_chat_template` conversations, `train_on_responses_only` (mask user turns), **no system prompt in the training data** (persona lives in the assistant turns), 25–50 % general chat, 1–3 % refusals/clarifying-question examples for off-topic prompts.
* Export: `model.save_pretrained_merged("merged", tokenizer, save_method="merged_16bit")` then `python llama.cpp/convert_hf_to_gguf.py merged --outfile m-F16.gguf --outtype f16` and `llama-quantize m-F16.gguf m-Q4_K_M.gguf Q4_K_M` (do the conversion ourselves with a llama.cpp ≤ **b10175** checkout so the audit image can load it; `save_pretrained_gguf(..., quantization_method="q4_k_m")` also works but pulls its own llama.cpp). Unsloth's own caveat: "incorrect chat template" is the most common cause of poor results after export — verify the GGUF's `tokenizer.chat_template` renders under b10175 and matches training. Known 2026 bug: `save_pretrained_gguf` on Qwen3.5-9B text-only fine-tunes ("config.json does not exist", unslothai/unsloth#4534) — another reason to convert manually.
* Which FP bases are realistic under 8 GB/4-vCPU no-AVX (from R-other, not re-verified here): Qwen3.5-2B/4B, Qwen3-1.7B/4B, Llama-3.2-3B, Gemma-3-1B/4B, SmolLM3-3B, MiniCPM4-0.5B/8B (FP). Unsloth cannot be used for the BitCPM QAT checkpoints (§5.2).

### 5.2 Fine-tuning the ternary BitCPM-CANN checkpoints

**5.2.1 What exists (verified today on HF):**
* `openbmb/BitCPM-CANN-{0.5B,1B,3B,8B}-unquantized` (Apache-2.0, all updated 2026-05-23, ~9.3–9.6 k downloads each). Card: *"the **unquantized QAT (Quantization-Aware Training) checkpoint** … designed for **continued pre-training and fine-tuning**. It preserves full-precision latent weights with ternary fake quantizers (weights → {-1, 0, 1} with group-wise scaling, trained via STE) defined in `modeling.py`"*; *"⚠️ This model is NOT for direct inference."*; *"The **only requirement** is that the forward pass must go through the bundled `modeling.py` … Load with `trust_remote_code=True` and do NOT replace or bypass the model's forward logic."*
* Sizes: 1B `pytorch_model.bin` 3.24 GB (bf16 ⇒ ~1.6 B params incl. 73,448×2048 embeddings; Llama arch, 28 layers, hidden 2048, GQA 16/2); 3B 7.21 GB (~3.6 B; 32 layers, hidden 2560, 32/2 heads); 8B 16.37 GB (~8.2 B; MiniCPM arch, 32 layers, hidden 4096, 32/2 heads, `vocab_size 73448`, longrope, `scale_emb 12`, `scale_depth 1.4`, `dim_model_base 256`). All use the same ChatML template (`<|im_start|>role\n…<|im_end|>`).
* Bundled code (read from `BitCPM-CANN-8B-unquantized/`): `modeling_minicpm.py` — `class LinearQuantizer(nn.Linear)` whose `forward` does `weight_tensor = self.quantizer(self.weight)`; `SteTernaryQuantizer.forward`: `scales = 1.0 / (x.abs().mean(dim=1, keepdim=True).clamp_(min=1e-5)); x_q = (torch.clamp(torch.round(x * scales),-1,1) / scales); … return x + (x_q - x).detach()` — i.e. **per-output-row (group_size = -1) absmean ternarisation with STE**, applied to `q/k/v/o_proj` and `gate/up/down_proj` only. Embeddings, `lm_head`, RMSNorms are ordinary bf16 (these become F16/Q6_K in the GGUF).
* Training scripts (`example/`): `train_sft.py` (HF `Trainer` + DeepSpeed, chat-template tokenisation, `--train_on_prompt false`), `run_sft.sh` (defaults: **8 GPUs, `per_device_train_batch_size 2`, `MAX_SEQ_LENGTH 8192`, `--max_steps 100 --learning_rate 2e-5 --lr_scheduler_type cosine --warmup_ratio 0.2 --weight_decay 0.0 --bf16 --gradient_checkpointing`, ZeRO-2 by default, `ds_config.json` = ZeRO-3 + CPU offload**), `requirements.txt` (`transformers==4.46.3 … deepspeed==0.16.2 datasets==3.1.0`), smoke-test logs `gpu_sft.csv` (UltraChat-200k SFT: loss 1.15 → 1.03 over 100 steps; `train_runtime 183.9 s`, `8.70 samples/s`, ≈ 71 k tokens/s across 8 GPUs, GPU model not stated) and `qat-convert.py` (`--quant_type ternary --group_size -1` fuses the fake quantiser into pseudo-quantised bf16 weights, same format as the inference repos).
* Downstream GGUF path (verified in our `opt/llama.cpp` b10360 tree): `convert_hf_to_gguf.py --outtype tq2_0` writes 2-D linear weights as **TQ2_0** and forces `token_embd`/`output` to **F16** ("TODO: use Q4_K and Q6_K"); TQ2_0 blocks use max-abs scaling per 256-block, which is **lossless** on already-ternary per-row weights. Then `llama-quantize` (with `--token-embedding-type/--output-tensor-type`) to reproduce the official file's head/embedding types, then `opt/scripts/prune_vocab.py` (CJK vocab prune, −164 MB) exactly as for the shipped model.

**5.2.2 Can they be fine-tuned, and how, in ≤ 5 GPU-h?**
* **Full-parameter QAT SFT (the way OpenBMB does it) — yes for 1B and 3B, no for 8B on one GPU.** AdamW bf16-mixed needs ≈ 12–16 B/param (bf16 weights + bf16 grads + fp32 m,v [+ fp32 master]) ⇒ 1B ≈ 20–26 GB, 3B ≈ 43–58 GB (fits an A100-80G; use `adamw_bnb_8bit`/`paged_adamw_8bit` to bring 3B to ~30 GB), 8B ≈ 100–130 GB ⇒ single-GPU only with ZeRO-3 CPU offload (needs >128 GB host RAM, throughput collapses). Time (*inference from `gpu_sft.csv` ≈ 9 k tok/s per GPU for 1B*): 5–10 M tokens of SFT ≈ 10–20 min (1B), 30–60 min (3B). Hyper-parameters: keep OpenBMB's `lr 2e-5` (or 1e-5), cosine, `warmup_ratio 0.2`, `weight_decay 0`, bf16, grad-ckpt, `max_seq_length 2048–4096`, **1 epoch**, effective batch ≥ 64 k tokens.
* **LoRA on the QAT checkpoint — technically runs, but the result cannot reach the audit intact.** PEFT would wrap `LinearQuantizer` (an `nn.Linear` subclass), so the base path still ternarises, but the LoRA delta `BA` is full-precision. Merging (`merge_and_unload` → `qat-convert.py`) adds `BA` to the latent weights and **re-rounds to {−1,0,+1}·scale**: only entries pushed across a ±0.5·mean(|w|) threshold change, so the merged ternary model ≈ base + sparse random flips, not the tuned function. Keeping the adapter separate is not an option (audit = single GGUF through `llama-bench`/judge chat; QVAC's BitNet LoRA work keeps FP16 adapters unmerged at inference, https://huggingface.co/blog/qvac/fabric-llm-finetune-bitnet). TII's `onebitllms` toolkit states flatly: **"LoRA is not supported with this package and remains a very interesting research question."** (https://github.com/tiiuae/onebitllms). Unsloth loads `LlamaForCausalLM` with its own kernels ⇒ bypasses `modeling.py` ⇒ trains latent weights *without* the fake quantiser ⇒ guaranteed drift. **Do not use Unsloth/LoRA for BitCPM.**
* **Non-ternary-tensor tuning (embed + `lm_head` + norms only)** — a cheap, GGUF-faithful middle path (*our proposal, not in any OpenBMB doc*): freeze every `LinearQuantizer.weight`, train `embed_tokens` (73,448×4,096 = 300 M for 8B), `lm_head` (300 M), RMSNorm gains; optimizer state ≈ 600 M params ⇒ 8B fits on one 80 GB GPU with grad-ckpt (weights 16.4 GB bf16 + activations); the trained tensors are stored F16/Q6_K/Q4_K in the GGUF, so the fine-tune survives conversion almost exactly. Capacity is limited (style/format/answer-shape shifts, some vocabulary preference), which is precisely what "no system prompt tutor persona" needs. Try this for 8B if the bake-off keeps 8B.
* **Risk of quality collapse** — evidence and mitigations:
  * The QAT models already sit 3–5 pts below FP (card table: 8B ternary GSM8K **85.75 vs 91.51**, MMLU 70.65 vs 75.83; "1B/3B/8B models retain 95.7%–97.2%"; 0.5B only 90.1 % — "quantization perturbation is more damaging when model capacity is limited"). Small-data SFT with STE can flip many ternary states; the OpenBMB smoke logs show loss falling monotonically at lr 2e-5 on UltraChat (no instability in 100 steps), which is the only public evidence that short SFT is benign.
  * Mitigations: lr ≤ 2e-5, warmup 0.2, 1 epoch, ≤ 10 M tokens, ≥ 25 % general chat, `train_on_prompt false`; **measure the ternary flip-rate** after `qat-convert.py` (fraction of weights whose ternary state changed vs the released pseudo-quantised checkpoint — cheap to compute; expect ≪ 1 % for a healthy run); gate on the §4 battery (ARC-C, GSM8K, AfriMMLU-math, JAMB) before/after; keep the pre-SFT GGUF as fallback.
  * Converting an FP model to ternary ourselves is out of the question: HF's 1.58-bit recipe needed 10–100 B tokens on Llama-3-8B (https://github.com/huggingface/blog/blob/main/1_58_llm_extreme_quantization.md).

**5.2.3 Concrete pipeline (1B/3B full QAT SFT)**
```bash
pip install "transformers==4.46.3" "deepspeed==0.16.2" "datasets==3.1.0" accelerate  # OpenBMB pins
huggingface-cli download openbmb/BitCPM-CANN-3B-unquantized --local-dir bitcpm3b-unq

  --data_path sft.parquet --max_seq_length 2048 --output_dir out --per_device_train_batch_size 4 \
  --gradient_accumulation_steps 8 --num_train_epochs 1 --learning_rate 2e-5 --lr_scheduler_type cosine \
  --warmup_ratio 0.2 --weight_decay 0.0 --bf16 --gradient_checkpointing --train_on_prompt false \
  --optim adamw_bnb_8bit --deepspeed bitcpm3b-unq/example/ds_config_z2.json --seed 42
python bitcpm3b-unq/qat-convert.py --input_bin out/pytorch_model.bin --output pq/pytorch_model.bin --quant_type ternary --group_size -1
# copy config/tokenizer from openbmb/BitCPM-CANN-3B (inference repo, no auto_map) next to pq/pytorch_model.bin
```
