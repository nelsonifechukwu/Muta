# V5 release gate

Date: 2026-10-09. This plan records the release workflow for the existing, uncommitted v5 changes; it does not authorize unrelated cleanup or a production service deployment.

1. Inventory and review the complete worktree, including staged deletions and untracked files. Preserve user work and exclude local secrets and generated outputs. Split source into coherent commits only after the tests and adversarial review identify any corrections.
2. Run Python, browser-client, desktop, contract, and package-specific checks. Inspect the changed desktop UI in both themes and on a narrow viewport, and launch a Mac build from the exact release commit for a startup smoke test.
3. Push a verified source commit to `main` without rewriting history. Build the four offline targets from that immutable commit using the established local/macOS and isolated GCP workers. Check archive integrity, architecture, source identity, bundled UI and model manifest, default tutor model, and adjacent SHA-256 files.
4. Publish a separate v5 GitHub release and upload the exact accepted set to the user-provided `Muta-version-5` Drive folder and the existing GCS package bucket. Preserve earlier releases and Drive folders. Read each destination back for names, sizes, digests where available, and duplicate counts.
5. Stop temporary build VMs, report any non-blocking limitations, and hand over the launched Mac app for visual testing. Do not silently promote the GCP production service; package publication and service deployment are distinct operations.

Release gates: no known P0/P1 defects, clean source identity, all four target archives and manifest present, no secrets in commits or logs, and final remote parity. A failed gate pauses publication rather than relabelling an incomplete set as v5.
